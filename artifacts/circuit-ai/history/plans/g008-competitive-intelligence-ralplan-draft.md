## Outcome and boundaries

Deliver a measured, reproducible G008 training/evaluation pipeline that improves rollout throughput and learns a policy competitive against held-out opponents. G007 is the baseline, not a success proxy: benchmark measured about 1,275 env steps/s with 3.195 s rollout vs 0.018 s optimizer, and step-300 won 1/64 vs `open-space` despite 58/64 vs step-0.

G008 is **approved only if all hard gates pass**: (1) the **median of five** unprofiled measured repeats is >=10,000 completed two-agent arena transitions per second on the single frozen principal config and Kaggle single-T4 runtime defined below (one joint `step` is one env step); (2) >=60% observed wins against every final unseen adversary, >=512 games per opponent, reporting Wilson 95% intervals; (3) no statistically significant validation regression against incumbent on any primary opponent under the executable paired protocol below; and (4) selected checkpoint exported as self-contained ONNX and validated in a real local browser match. If any gate is missed after bounded experiments, publish the best evidence and exact bottleneck and leave G008 **not approved**—do not redefine a target or imply success.

Hard isolation: exact `open-space` implementation/parameters and every `open-space` game/demo/label/generated example remain **final-evaluation-only** and are explicitly included in the final gate. Do not use this opponent for training, imitation, reward shaping, validation or checkpoint selection. Train, validation and final **opponent** policy identities and code/config/model hashes are mutually disjoint; the frozen candidate checkpoint is a target policy, not a held-out opponent, and may be evaluated in validation/final after training. All seed values/game conditions are split-disjoint; every game record is keyed by `(split, opponent_id, opponent_hash, target_checkpoint_hash, config_hash, seed, target_seat)` and must be unique to exactly one split. No final seed/game tuple or final-opponent identity/hash may occur in training, demonstrations, reward design, validation or promotion input. Missing provenance, overlap, hash mismatch, or incomplete validation coverage fails closed. Freeze candidate before final suite; do not tune/promote after inspecting it. Keep opponent pool internal; no viewer tournament UI, society simulation, hosted service or paid services. Do not implement DDP unless a measured single-vs-dual experiment demonstrates an end-to-end benefit; no such experiment is presumed necessary.

## RALPLAN-DR: decision frame

### Principles
1. **Measure first, preserve an oracle:** deterministic Python `engine.py` remains the rules reference; every optimized engine has differential tests and cannot trade semantic correctness for speed.
2. **Optimize the dominant path, not the visible GPU:** rollout is the measured bottleneck, so profile arena stepping, Python loops, action selection, allocation, device/host transfer and sync separately before changing the backend.
3. **Learn against a curriculum, evaluate against untouched opponents:** strategic quality is selected using a disjoint validation league; exact open-space and locked final opponents remain unseen until final test.
4. **Promote evidence, not update counts:** checkpoints require paired validation quality and anti-regression; training length alone is never a criterion.
5. **Bound complexity and spend:** take the simplest reproducible performance/learning gain; inspect current free Kaggle quota before each remote batch and stop on quota/time/output limits without billing changes.

### Top decision drivers
1. **End-to-end measured gain with parity:** qualify a backend only if it meets the objective paired-repeat criterion below for >=10% update-only training throughput gain over the immediately preceding winner, with no parity failures; separately report cold JIT/import cost and steady-state rate. Use exact same fixed states/actions/workload/device and disclose timing boundaries.
2. **Opponent generalization and test isolation:** ≥60% observed wins against each final unseen adversary over ≥512 games; choose checkpoints only on separate validation, with prescribed paired regression control.
3. **Operational reproducibility:** a Kaggle run is only justified after local correctness/performance screening; archive code revision, config, seeds, opponent hashes, software/hardware, raw repeats, game-level outcomes/replays, model hashes and viewer acceptance. Respect actual free quota.

### Viable approaches

| Option | Description | Pros | Cons / decision |
|---|---|---|---|
| A — staged profiling, low-risk cleanup, then one compiled candidate (SELECT) | Establish baseline/profile; remove avoidable per-tick sync and Python work; retain scalar oracle; benchmark NumPy control and at most one Numba-compiled candidate. Rust/PyO3 is excluded from G008 absent new measured evidence and separate bounded approval. | Small reversible steps; validates true bottleneck; Numba is recommended first compiled experiment; NumPy is a control; preserves fallback and parity; lower packaging friction than Rust on Kaggle. | Selected. Needs explicit warm/cold timing and Python-oracle differential harness. Numba availability/versions must be checked in the live Kaggle image; do not assume current toolchain. |
| B — immediately port full engine to Rust/PyO3 | Replace simulator before measurement, then integrate native extension into Kaggle runner. | Potential high raw simulation speed; static implementation can be compact. | Rejected for G008: highest build/ABI/Kaggle integration and semantic drift risk; could optimize a non-dominant portion; difficult attribution without oracle/profile baseline. Rust is not in the experiment ladder; future reconsideration requires measured profile evidence and a separate plan. |
| C — stay pure Python/NumPy only | Optimize loops/data layout with existing ecosystem and no compiled runtime. | Simplest install and debugging; easiest reproducibility; safe control arm. | Keep as fallback/control, not presumed sufficient: current Python batch wrapper still loops scalar engine and baseline is 7.8x below target. Only accept as final if benchmark reaches gate. |

**Selected decision:** Option A, with a mandatory no-optimization baseline and finite one-change-at-a-time gates. NumPy is a control; at most one Numba candidate is allowed. Rust/PyO3 is excluded from G008. Do not implement DDP absent evidence because optimizer time is negligible relative to rollout.

### Stage 3 — promotion, frozen final evaluation, artifact versioning
- Extend `training/eval/lc_eval.py` to configurable opponent sets, >=512 games/opponent, reproducible seeds, alternating target seats, W/D/L, Wilson 95%, per-game outcomes and replay paths. Version the report/schema (proposed `lc-eval/2`) rather than weakening immutable `lc-eval/1`; include split identity/lock status, opponent code/model hashes, seed lists, game count, protocol version, candidate and incumbent IDs.
- Implement the executable validation promotion protocol. For each primary validation opponent, pair candidate and incumbent outcomes at identical `(opponent hash, seed, target_seat)` game condition; both seats for a seed are retained as a cluster. Map each game's W/D/L to score 1/0.5/0, form per-game candidate-minus-incumbent deltas, and use the **seed cluster** as the paired resampling unit so both seats remain together. Require complete, non-missing coverage of every primary opponent and the frozen matrix (proposed 256 seeds × 2 seats = 512 paired games/opponent); any mismatch/incomplete cell means **do not promote**.
- For every opponent report point mean paired score delta and two-sided percentile paired-bootstrap 95% CI from **10,000** seed-cluster resamples with replacement, PRNG seed **20261020**. For regression test compute one-sided lower-tail bootstrap p-value under the centered null: subtract observed mean delta from each seed-cluster delta, resample centered clusters 10,000 times with same PRNG stream, then `p=(1 + count(resampled_mean <= observed_mean_delta))/(10001)`. Hypothesis is H0: mean delta >=0 vs H1: mean delta <0. Apply **Holm-Bonferroni** to these one-sided p-values across the predeclared family of all primary validation opponents; significant decline iff adjusted p < 0.05 and observed delta < 0. Block promotion if any primary-opponent decline is significant. Promote only if no adjusted regression is significant **and** the predeclared equal-weight macro-average validation score delta across all primary opponents is positive; this is a selection rule, not a final success claim.
- Synthetic tests must cover (a) identical candidate/incumbent outcomes/no regression, (b) clear negative candidate delta triggers veto, (c) all ties and degenerate bootstrap, (d) correlated two-seat seed clusters stay together, (e) Holm with multiple opponents where only one adjusted result is significant, and (f) missing/duplicate pair coverage rejects promotion. Persist bootstrap seed, replicate count, per-seed cluster deltas, raw/adjusted p-values, interval and decision in report. Never read locked final set in selection code.
- Generate one immutable final report after freezing selected candidate. Report each required final adversary >=512 games and Wilson 95%, all W/D/L separately, seeds/seats/replay hashes, protocol and model hash. Gate is observed win rate >=60% for every adversary; Wilson lower bound is reported but is not itself required to exceed 60%.
- First determine which G008 evidence cannot be represented without changing existing semantics. Preserve `lc-run/1` and `lc-eval/1` as-is for old G007 artifacts. Add a narrow versioned G008 schema only for genuinely new required fields: (a) throughput numerator/timing protocol/raw repeats; (b) split manifest hash/provenance and opponent pool references; (c) validation paired-promotion report; and (d) 512-game evaluation records. Proposed `lc-eval/2` only if eval fields/count/version need widening; do not silently relax v1's fixed 64-game schema. Extend manifest schema/version only if it cannot reference the separately validated G008 evidence sidecar. Add schema fixtures/validators proving old G007 bundles still load and G008 manifests fail closed on missing hashes/split metadata. Viewer changes are compatibility-only to load/display new report fields; **no league, opponent selection, or tournament UI**. Continue validating single-file ONNX and reject unlisted external data.
- Export the frozen promoted model as single-file ONNX. Run ONNX checker/hash/metadata validation and real browser test using local viewer: load downloaded run, confirm verified checkpoint, run fresh seeded match, inspect actions/outcome; no server inference. Preserve browser evidence.
- **Gate:** no final evaluation until candidate ID, code/config, opponent and seed manifests are frozen and their hashes recorded. If final result fails either numeric gate, do not reselect using that test; classify G008 as not approved and propose a new G009 validation cycle with a newly collected holdout.

## Research / evidence anchors
