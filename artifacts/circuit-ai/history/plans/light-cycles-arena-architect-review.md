# Architect Review — Light Cycles AI Arena

**Current verdict: APPROVE (cycle 2).** Cycle 1 was `ITERATE` because browser-local inference and the artifact contract were unresolved; Revision 1 resolves those planning findings. No implementation source was changed. Critic review remains pending.

## Summary

The plan consistently narrows the MVP to a personal two-agent self-play arena, local replay/metrics viewing, Kaggle training automation, and measured throughput; it correctly excludes the Grid society, human-vs-AI, and full tournament scope. Retain a Python-canonical engine/training/evaluation implementation and a local web viewer, but resolve “browser-local inference” explicitly: for MVP, load checkpoints and generate fresh local evaluation/self-play matches through the canonical Python runner, then inspect their replay in the browser. This preserves trained-checkpoint use without a second simulation engine or an unvalidated browser model runtime.

The main blocker is contractual rather than conceptual: the PRD allows either browser inference or replay-only viewing, while acceptance criteria and user intent mention using trained checkpoints locally. Before execution, state which runtime generates a local checkpoint match, how it produces a replay, and what precise versioned replay/manifest/checkpoint contract crosses the Kaggle-to-local boundary.

## Findings and evidence

1. **Runtime boundary is unresolved and weakens a core workflow.** The draft's recommended Option A is Python-canonical, but conditions browser inference on later acceptance and leaves local matches to stored replay/local runner output (`.omx/plans/light-cycles-arena-ralplan-draft.md:22-26, 55-56`). PRD expressly makes browser inference conditional (`.omx/plans/light-cycles-arena-prd.md:32-36, 56-57`), although its outcome is to transfer a Kaggle checkpoint into the local viewer (`:6-7`) and the original requirement says to observe trained-checkpoint behavior locally (`.omx/specs/deep-interview-light-cycles-arena.md:9-13`). A replay-only viewer over Kaggle-produced games does not, by itself, prove that a downloaded checkpoint is loadable and usable locally.
   - **Decision recommended:** Python remains the only canonical rules and policy-inference runtime. Add a local Python command/runner that loads a downloaded checkpoint, runs a fresh seeded match or evaluation batch, writes the same replay schema, and the browser displays it. Browser-local inference and a second TypeScript engine are explicitly out of MVP. This creates no cross-engine game-rule parity obligation; model/action version compatibility is still validated in Python.

2. **Replay and manifest are named but not defined as interoperable contracts.** Plans request versioned replay/artifact formats, hashes and round trips, but defer all fields and formats to milestone 1 (`.omx/plans/light-cycles-arena-ralplan-draft.md:46-50`; `.omx/plans/light-cycles-arena-prd.md:32-35`; `.omx/plans/light-cycles-arena-test-spec.md:23, 39`). The hash criterion is not reproducible until canonical serialization, float handling, ordering, and hash scope are specified. The viewer cannot safely load a checkpoint/replay across Kaggle and local code without stable identifiers for engine, observation/action schema, policy, and artifact versions.
   - **Decision recommended:** freeze a minimal manifest schema and replay schema before parallel implementation: schema versions; run/checkpoint IDs and step; engine/observation/action/reward versions; configuration and seeds; policy/model format and framework version; evaluation protocol/opponent identity; metric units/sample counts; device/software metadata; replay initial state plus per-tick joint actions or compact state snapshots; terminal cause/result; and canonical content digest. Prefer replay records that remain viewable without depending on a live Kaggle runtime (full state snapshots or a clearly version-pinned action-reconstruction contract). Avoid choosing a compression/library dependency until measured artifact size justifies it.

3. **Reproducibility claims exceed the current seed contract.** Fixed seed/config yielding identical transitions is appropriately tested (`.omx/plans/light-cycles-arena-prd.md:59-64`; `.omx/plans/light-cycles-arena-test-spec.md:19, 39`), but plans do not identify the PRNG algorithm, stream splitting for vector arenas/agents, episode-reset behavior, or whether the guarantee is same runtime/version rather than cross-platform bitwise identity. Neural inference can also introduce nondeterministic behavior if GPU kernels or sampling are used.
   - **Decision recommended:** scope determinism to a pinned engine/schema/runtime contract; specify per-arena/per-agent PRNG streams and reset derivation; use deterministic tie-breaking and inference mode for evaluation; record seed derivation and exact actions in replays. Do not promise cross-device bitwise PPO training reproducibility unless it is separately measured and supported.

4. **Kaggle automation safety is directionally good, but its external side-effect boundary needs sharper command semantics.** The plan correctly forbids session-time Kaggle runs and credential use, requires mocked CLI flows, explicit run/version selection and secret redaction (`.omx/plans/light-cycles-arena-ralplan-draft.md:58-59, 83-90`; `.omx/plans/light-cycles-arena-test-spec.md:53-58`). However, “dry-run” and “user-invoked” alone do not define which command may submit remotely, nor how stale/ambiguous kernel identity, running-job conflicts, missing auth, or partial output downloads are handled.
   - **Decision recommended:** keep Kaggle CLI as an isolated adapter (rather than introduce an API client unless a documented CLI gap requires it); make status/download read-only operations explicit, require an explicit submit subcommand plus target kernel/version and a confirmation flag, default all examples/tests to dry-run, never invoke submission as part of app startup/build/viewer flows, and validate downloads into a temporary directory before promoting them into the local artifact library. Document the exact supported credential lookup path from official docs at implementation time; do not copy credentials into repo files or log command environments.

5. **Acceptance and test criteria are broad but mostly appropriately measurable; separate evidence from learning success.** Deterministic collision fixtures, optimizer-update assertions, artifact round trips, mocked Kaggle operations and fixed-seed evaluation are concrete (`.omx/plans/light-cycles-arena-test-spec.md:17-30, 32-46`). The plan correctly avoids arbitrary hardware-independent performance thresholds and requires reporting available GPU use (`.omx/plans/light-cycles-arena-test-spec.md:48-51`). However, “held-out checkpoint progress” and “higher useful throughput” cannot be acceptance pass/fail without a prescribed protocol and objective; one stochastic comparison cannot establish learning. Also CUDA validation is conditional in generic CI and later requires Kaggle/available GPU evidence (`.omx/plans/light-cycles-arena-prd.md:61-67`; test spec `:24, 64`).
   - **Decision recommended:** define fixed held-out seed set, opponent/baseline identity, match count, checkpoints compared, and report win/draw/loss with uncertainty/sample count; make the MVP criterion “evaluation artifacts produced and reportable,” not “learned improvement achieved.” For throughput, require benchmark records and an explicit selected configuration/rationale, with no universal numeric threshold. Label actual Kaggle GPU smoke/throughput as an external validation item until the user runs it; never imply it has passed based on local CPU or mocked CLI tests.

6. **Scope and dependency risks are manageable if sequencing is honored.** The greenfield resource map is intentionally provisional (`.omx/plans/light-cycles-arena-ralplan-draft.md:33-42`), and milestones put deterministic contracts before PPO, viewer, and Kaggle integration (`:44-62`). This is sound. Main integration risks are action/observation drift, model conversion if browser inference is accidentally reintroduced, replay volume, Kaggle notebook output limits, and CPU rollout starvation of GPU updates. The plan cites current official Kaggle/PyTorch research and marks quota/runtime details mutable (`.omx/plans/light-cycles-arena-ralplan-draft.md:6, 53, 58-62`; PRD `:69-73`). No assumption about actual T4 x2 allocation or Kaggle execution is verified here.

## Strongest antithesis

**Steelman:** Use a TypeScript engine and browser-native inference as the actual product, while Python implements only training. The user asked to use training locally and originally proposed browser inference; fresh matches from a downloaded checkpoint directly in the browser would be more immediate and engaging than running a Python command and loading its replay. Browser execution avoids a local Python service/process boundary and gives the viewer an interactive, shareable artifact experience.

**Why not choose it for this MVP:** it creates duplicated game semantics (simultaneous collision ordering, observation encoding, legal action ordering, terminal resolution) and model-export/runtime parity obligations before the learning loop is known to work. This adds a second engine and ONNX/browser inference integration to an already greenfield PPO/Kaggle pipeline. The plan itself recognizes parity as a top driver and documents this option's drift risk (`.omx/plans/light-cycles-arena-ralplan-draft.md:17-26, 83-86`). The user's goal is to inspect the training experiment, not specifically to run policy inference inside a browser; Python-generated fresh checkpoint matches plus replay playback provide that evidence at lower MVP risk.

## Tradeoff tension

The valuable user experience is “I downloaded a checkpoint and can immediately watch it play,” while the lowest-risk training architecture has one Python engine and one Python policy runtime. Browser-native inference optimizes immediacy and deployment simplicity but introduces model-runtime conversion and a duplicated rules engine; Python-generated local replays preserve semantic parity but require a local Python command/runtime and an artifact handoff. The latter is recommended until the MVP has a verified policy worth interactive play.

## Recommended synthesis / decisions to carry into the plan

1. Approve Python as canonical for simulation, training, evaluation, and local checkpoint inference. The web app is a local replay/metrics viewer; a local runner creates fresh replay artifacts from chosen checkpoints. No TS engine or browser model runtime in MVP.
2. Add a pre-implementation contract gate specifying manifest/replay/checkpoint schemas, deterministic seed streams, collision priority, observation/action encoding, replay hash canonicalization and compatibility/error behavior. Persist a small schema fixture consumed by trainer, local runner, Kaggle packaging, and viewer.
3. Define evaluation protocol and sample counts before training code; acceptance proves reproducible reporting and artifact production, not guaranteed PPO improvement.
4. Specify Kaggle submit as an explicit, opt-in side-effecting command; status/download are explicit operations; dry-run/mocks are default for verification; validate output atomically and do not claim live Kaggle/GPU success until the user invokes a real run.
5. Benchmark vectorized rollout and PPO updates separately and end-to-end. Compare one vs two GPUs only when both are actually available and the identical workload can be run; select on measured arena/step throughput plus update time, never occupancy alone.

## Explicit remaining issues / gates

- **Blocking for Ralplan approval:** revise PRD/draft/test spec to make the Python-local inference + generated replay workflow a committed MVP behavior and remove conditional “browser inference” acceptance language.
- **Blocking before implementation split:** publish concrete versioned artifact/replay interface and its fixture; decide whether replays contain all state frames or deterministic action streams and specify hash canonicalization.
- **Must be explicit before PPO implementation:** fix baseline policy, evaluation seeds/count and self-play opponent/checkpoint sampling protocol; record sample count and uncertainty.
- **Must be explicit before Kaggle submit implementation:** exact opt-in/confirmation flow, kernel identity/version selection, safe temporary output staging, and auth/error/secret-redaction behavior.
- **External validation outstanding by design:** actual Kaggle quota/runtime, CUDA optimizer smoke, T4 single/dual benchmark, and remote submit/status/download round trip are not established by these artifacts or this review. No credentials or remote job were used.

## Cycle 2 — Revision 1 re-review

**Verdict: APPROVE.** The material findings from cycle 1 are resolved in the revised RALPLAN, PRD and test spec. In particular, browser-local trained-checkpoint inference is now a required MVP behavior, not an optional branch; the plan accepts a TypeScript engine plus ONNX Runtime Web and makes shared Python/TypeScript parity a hard gate. Replay/manifest formats, seed stream scheme, evaluation protocol and Kaggle side-effect controls are now concrete enough to proceed through the Critic gate and into a contract-first implementation plan. No source implementation or Kaggle job was run as part of this review.

### Prior findings disposition

1. **Browser inference/runtime boundary — resolved.** PRD requires fresh, network-disabled browser matches from downloaded ONNX checkpoints (`.omx/plans/light-cycles-arena-prd.md:48-51, 64-70`); RALPLAN explicitly selects Python reference/training plus TypeScript browser engine/ONNX inference and rejects the Python-only replay alternative (`.omx/plans/light-cycles-arena-ralplan-draft.md:24-32`). This preserves the original requirement at the accepted cost of duplicated rules.
2. **Artifact/replay schema and determinism — resolved for planning.** The PRD now lists `lc-run/1`, `lc-replay/1`, checkpoint identity/formats, SHA-256 digest scope, collision causes/actions, compatibility failures and deterministic stream contract (`.omx/plans/light-cycles-arena-prd.md:23-46`). Test spec adds a cross-runtime PCG32 vector contract, canonical digest fixtures, compatibility/path-traversal checks, and engine/policy parity cases (`.omx/plans/light-cycles-arena-test-spec.md:17-31`). A small shared fixture corpus is a required first milestone, not an optional later hardening (`.omx/plans/light-cycles-arena-ralplan-draft.md:47-56`).
3. **Kaggle submission boundary — resolved.** A single explicit `submit` command requires kernel, source revision, and `--confirm`; status/download are explicit, bounded/read-only operations; output is staged, validated, and atomically promoted (`.omx/plans/light-cycles-arena-prd.md:55-59`; test spec `:67-75`). The workflow excludes credentials and remote activity from delivery/tests. The official CLI supports kernel/version references for status and output, so the wrapper can bind an explicit version into the CLI kernel reference and validate downloaded `run_id` against the requested ID; implementation should preserve that mapping.
4. **Evaluation/verification measurability — resolved.** The target has two specified 64-game matchups over held-out seeds 0–31, seat swaps, fixed baseline/step-0 identities, Wilson intervals, survival/collision results, and per-game records; acceptance requires complete report/artifact production, not guaranteed learning gain (`.omx/plans/light-cycles-arena-prd.md:26-30, 67-75`; test spec `:47-57`). Throughput criterion records named workload, device/use/timings and selection rationale without an inappropriate universal speed threshold (test spec `:77-79`). CUDA and Kaggle live validation are honestly marked external until user execution.
5. **Scope/integration — consistent.** The accepted two-engine architecture increases integration work but does not reintroduce society simulation, human play, tournaments, or hosting; the resource map and milestones gate PPO/viewer work on engine and parity contracts (`.omx/plans/light-cycles-arena-ralplan-draft.md:36-68, 81-94`; PRD `:61-76`).

### Strongest antithesis

The strongest objection remains the original Python-only recommendation: a canonical Python engine and checkpoint runner with a browser replay viewer would avoid duplicated collision logic, ONNX export/runtime conversion, cross-language seeded-random implementation, and parity maintenance. For a personal research game whose central risk is proving PPO actually learns, browser-local inference is a sizable up-front implementation tax and could delay the actual training experiment.

### Tradeoff tension

Immediate, offline browser use of a downloaded checkpoint is a direct original product requirement, while a single Python runtime is the lower-risk way to preserve rules and inference parity. Revision 1 explicitly chooses the user-facing behavior and contains the resulting cost behind fixtures and staged gates; this is a deliberate trade, not a claim that the dual-runtime design is cheaper or intrinsically superior.

### Synthesis

Proceed with the selected Python-reference/TypeScript-browser/ONNX design, but execute in dependency order: first materialize a tiny shared v1 contract/fixture and prove ONNX export-load-action parity, then Python rules, TypeScript differential parity, PPO/export, offline browser match/replay, and only then polish. If the first runtime compatibility proof or parity fixture fails, stop and return to architecture/user with concrete evidence; do not silently fall back to replay-only viewing. This preserves the original requirement while limiting sunk cost.

### Remaining implementation gates (not Ralplan blockers)

- Before source lanes diverge, materialize the shared fixture/schema artifacts and choose one consistent location (the resource map still says `schemas/` **or** `shared/fixtures/`; `.omx/plans/light-cycles-arena-ralplan-draft.md:44`).
- The observation's exact tensor/vector shape/orientation is intentionally still assigned to the first interface fixture (`.omx/plans/light-cycles-arena-prd.md:24`); freeze it there before either engine implementation. Also freeze model architecture and supported ONNX opset/runtime after the required compatibility spike (`.omx/plans/light-cycles-arena-prd.md:46, 65`; RALPLAN `:49-50`).
- Digest fixtures must settle the canonical decimal-number rendering and explicitly exclude the self-digest field from hash input; clarify that the manifest's `files` list does not contain its own manifest digest to avoid a self-reference (`.omx/plans/light-cycles-arena-prd.md:33, 42`). These are straightforward contract-fixture details, not a reason to reject the selected architecture.
- For the Kaggle wrapper, map explicit wrapper `--version` to Kaggle's documented versioned kernel reference, then verify the downloaded manifest's run identity; never use the CLI's overwrite option for final artifact promotion. This is already consistent with PRD's staging/atomic/no-overwrite rule (`.omx/plans/light-cycles-arena-prd.md:56-59`).
- Still unverified externally: installed Kaggle CLI/runtime/quota, CUDA PPO update on Kaggle, ONNX behavior on the selected browser/runtime, and measured single/dual T4 throughput. These are validation work, not facts this planning review can claim.
