## Decisions

### Principal config and legacy boundary

Keep the frozen principal G007 PPO config byte-for-byte unchanged, including `seed=1234` and canonical config SHA-256 `0ec65b7978e26ecb13b893e76ec358d48c41428db96b0a60dd810f9f24f0e484`. The hash covers the existing principal config only; the G008 seed/run protocol remains a separate, versioned and separately hashed artifact.

Do **not** retroactively reinterpret G007's generic `seed` or infer an environment-root mapping absent from its historical run artifacts. Preserve G007 reports and their original semantics as legacy evidence, label their seed semantics `legacy-unspecified` wherever the artifact does not establish them, and exclude those runs from G008 paired comparisons. G007's three-repeat throughput result is historical, non-paired reference only: it cannot count as a G008 repeat, enter a paired speedup, or be mixed into the G008 five-repeat median.

For new G008 execution, the unchanged principal `seed=1234` is explicitly the model/PPO RNG seed only. An independently supplied `env_root_seed` identifies environment randomness. At the runtime boundary, the G008 adapter must map the existing field into model/PPO RNG initialization and seed every Python, NumPy, PyTorch CPU and CUDA RNG stream explicitly; it must pass environment roots through the environment seed API and never let a generic config seed silently reseed the environment. Record mapping version and all RNG snapshot identities. If the current trainer cannot do that without modifying the principal config/hash, add a protocol adapter/sidecar—not a principal-config field—or stop before benchmark execution. No G007 run is migrated in place.

This migration boundary includes config parsing, `TrainConfig`, model/PPO RNG initialization, rollout collection, every initial/reset environment seed, checkpoint save **and resume**. New checkpoints persist model/PPO seed, `env_root_seed`, derivation version, full derivation tuple/domain, partition/provenance and benchmark ancestry. Resume is accepted only if metadata is complete and matches the active frozen manifest/config/runtime protocol. Reject resume from a legacy checkpoint with unspecified seed semantics, missing/mismatched root/derivation metadata, or any benchmark-derived checkpoint. Independence tests prove that changing only `model_rng_seed` changes model/PPO RNG state but leaves environment-derived seeds unchanged, while changing only `env_root_seed` changes environment-derived seeds but leaves initial model/PPO RNG state unchanged.

Checkpoint migration must be **resume-equivalent**, not save-only: persist and restore the actual state bytes plus content identities for Python `random`, NumPy RNG (if NumPy is installed), Torch CPU RNG and every CUDA RNG. If a runtime intentionally has no NumPy dependency, record a versioned `numpy_rng_mode=no_numpy` declaration and test that no NumPy RNG is used; never silently omit this field. Persist/restore the environment derivation protocol and exact schedule cursor (next update/rollout/arena/game/reset tuple), live environment/vector state, PPO rollout/sampler position, optimizer/scheduler state, model state, training counters, and supported deterministic-backend flags/version/state (including relevant PyTorch/CUDA/backend settings). Define the supported resume boundary (prefer complete PPO-update boundaries; if mid-update resume is supported, persist all in-flight rollout/minibatch state). Resume must restore every component before collecting another observation or sampling an action.

Under the declared deterministic backend contract, a checkpoint/resume test runs a seeded trajectory uninterrupted and as save→process restart→restore, then asserts exact equality for the next environment-derived seeds and, in sequence, observations, sampled actions, transition outputs/rewards/dones, next model/PPO RNG bytes, model parameters and optimizer state after the next update. Unsupported nondeterministic kernels/backends must be explicitly declared and cannot be used to claim exact resume equivalence or paired determinism; do not silently downgrade the contract.

### Injective environment seed derivation and partitioning

Add a `benchmark` split to the versioned G008 seed plan, disjoint from G007 historical evaluation, train, imitation, validation and final. Freeze measured roots as `5,000,000`, `5,000,001`, `5,000,002`, `5,000,003`, `5,000,004` for paired repeats 0–4, selected from `5,000,000–5,000,255`. Freeze warmup roots as exactly `5,000,256` through `5,000,271`, inclusive. Assign the warmup list in order by `(implementation_version, backend_role, warmup_rollout_index)` for the four registered slots Python incumbent, low-risk candidate, NumPy control, and at most one Numba candidate; backend roles are incumbent/candidate, rollout index is 0 or 1. Unused slots remain unused, not reassigned. Each measured pair uses the root assigned to its repeat for both sides. These are environment roots and are not model seed 1234.

Every environment episode/reset seed must be deterministically derived by a versioned, domain-separated function from `env_root_seed` plus canonical tuple `(split/domain, paired_repeat_id or train_run_id, update_index, rollout_index, arena_index, episode/game_index, reset_index)`. For paired incumbent/candidate runs, backend role/version is provenance metadata but deliberately excluded from the derivation key, so both use the same derived seeds. Warmups include implementation/backend slot plus warmup rollout index. Define canonical encoding and digest-to-supported-integer conversion; validate the entire frozen finite schedule for collisions and reject duplicate derived seeds before execution. Domain labels distinguish `g008/train`, `g008/benchmark`, `g008/eval`, and nested update/rollout/arena/game/reset scopes. Each initial/reset call records root, complete tuple, derivation version and derived seed. Do not use arithmetic offsets or unlabelled `root + index`.

Freeze schedule counts: each measured repeat uses one root, exactly 3 PPO updates, 32 rollout ticks/update and 128 arenas/tick, or 12,288 completed joint transitions per backend/repeat. Five pairs yield 61,440 transitions/backend and 122,880 across both paired sides. Each registered implementation/backend slot gets exactly two full 32-tick × 128-arena warmup rollouts using its assigned roots; warmups are excluded from measured aggregates. Expand all repeat/backend/update/rollout/arena/initial-reset and subsequent-reset tuples into the frozen manifest and assert derived-seed uniqueness before running.

Benchmark roots are measurement-only. The benchmark runner may consume its own rollout transitions and returns within that invocation to perform its own throughput-only PPO updates. No benchmark episode, return, resulting weight, optimizer state, RNG state, replay or artifact may be consumed by any later training, imitation, reward design, validation, promotion, final evaluation or opponent-pool construction. Benchmark weights/optimizer state are discarded after timing/reporting and cannot seed a subsequent learning run. Enforce this via artifact provenance/content hashes and consumer checks, not split-name convention alone.

Exact `open-space` implementation/configuration/games/data remain final-evaluation-only, including under the benchmark split. No open-space policy/game may produce benchmark traces. A pure simulator fixture should be deterministically generated from a versioned fixed-state/action fixture; if a diagnostic fixture derives from games, its source must be a non-open-space benchmark source with complete provenance.

### Paired full-update gate versus fixed-fixture diagnostics

The **10,000 joint transitions/s hard gate is measured on full PPO updates**, not a fixed-fixture microbenchmark. Exactly five unprofiled measured repeats × exactly three PPO updates/repeat use the unchanged approved principal config and timing boundary: initialize/reset rollout environments, build observations, infer/sample actions, perform all environment transitions, transfer/synchronize as required, and complete the PPO optimizer update; exclude checkpoint serialization/export and report writing. Each repeat rate is 3 × 32 × 128 completed joint two-agent arena transitions / full update-only elapsed seconds; the median of five must be >=10,000 on the one-used-T4 reference runtime. Preserve the approved paired-intervention criterion: candidate median paired speedup >=10% and at least 4/5 pairs individually >=10% faster than the immediately preceding eligible implementation, with exact parity. Any fixed-state/action replay benchmark is diagnostic only and cannot satisfy the gate or select over full-update evidence.

For each G008 incumbent/candidate pair, use the same frozen initial model weights and optimizer state, model/PPO RNG state, Python/NumPy/Torch CPU/Torch CUDA RNG states, principal config, device/runtime and exact ordered environment-root/derived-seed schedule. Retain the actual canonical serialized bytes for initial model weights, optimizer state and Python/NumPy/Torch CPU/every CUDA RNG snapshot in a content-addressed store; SHA-256 identifies retained bytes but is not a substitute for them. For deterministic policy execution, retain versioned full-update rollout traces and separate canonical hashes for (1) input observation/state stream, (2) chosen action stream, and (3) resulting transition/output stream. Before timing comparison, require identical initial model/optimizer/RNG snapshot identities and matching input-state/action hashes; state-output mismatch is parity failure. If stochastic actions diverge, do not claim a comparable pair.

Retain a canonical versioned fixture/generator as an independently replayable diagnostic: generator source/version/hash, canonical input format, exact seed tuple, generated state bytes, action bytes and resulting output digest. Fixture execution is not a substitute for the full PPO update gate. Warmups are exactly two complete rollouts/version using assigned roots, marked `measurement_phase=warmup` and excluded from measured aggregates. The five measured pairs are marked `measurement_phase=measured`, keyed by `paired_repeat_id`, with alternating incumbent/candidate order preregistered. Report all pair inputs, raw timing boundaries and paired gains. G007 historical repeats are shown separately.

## Acceptance / stop conditions

- Principal config remains byte-identical with hash `0ec65b7978e26ecb13b893e76ec358d48c41428db96b0a60dd810f9f24f0e484`.
- G007 legacy seeds are not reinterpreted; G007 throughput remains non-paired historical context.
- G008 model RNG and environment root/derived seeds are separate, explicitly versioned and recorded; every episode/reset derivation is unique within the frozen manifest.
- Checkpoint resume validates and restores Python, NumPy (or explicit tested no-NumPy mode), Torch CPU/all CUDA RNGs, env root/derivation tuple/version, live env state/schedule position, model/optimizer state and deterministic-backend protocol; legacy/missing/mismatched/unsupported/benchmark-derived resumes fail closed, and resumed next-step outputs match uninterrupted execution under the declared deterministic contract.
- Exact five measured roots and 16 warmup roots are frozen and fully expanded to unique per-update/rollout/arena/reset derived seeds.
- All five measured pairs run exactly three PPO updates and retain identical initial model/optimizer/RNG snapshot bytes plus matching input-state/action digests; output digests are retained. Fixed-fixture speed does not count toward 10k.
- Paired intervention promotion retains median >=10% speedup and >=4/5 pairs individually >=10%; benchmark updates are ephemeral and no later consumer can read their descendants.
- Benchmark updates and all descendants are rejected at every actual non-benchmark consumer, including after attempted relabeling.
- If the runtime adapter, deterministic replay, injective derivation, or consumer checks cannot be established, do not launch a paired acceptance benchmark or training consuming these artifacts; report the gate unverified.

## Scope / risk

No principal config, model architecture, approved threshold, compute budget, opponent set, holdout policy or original gate changes. New protocol fields live in separately hashed manifests/reports. Principal risk is current generic-seed coupling; the adapter must be proven at real consumers before G008 work. Another risk is RNG/runtime drift or replay mismatch; snapshot identities and stream/output digests make this visible. Benchmark performance artifacts are intentionally non-reusable for learning or checkpoint selection.
