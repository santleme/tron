# G008 Ralplan — Architect Review

**Verdict: ITERATE**  
**Reviewed:** `.omx/specs/g008-competitive-intelligence.md`, `.omx/context/g008-competitive-intelligence-20261020T002306Z.md`, `.omx/plans/light-cycles-arena-prd.md`, `.omx/plans/light-cycles-arena-test-spec.md`, and the complete `.omx/plans/g008-competitive-intelligence-ralplan-draft.md`.

## Summary
The staged architecture is directionally sound: retain the deterministic Python engine as oracle, profile the rollout that dominates G007, gate compiled backends on differential parity and end-to-end gains, isolate the exact `open-space` opponent, and select using validation rather than final results. Do not start implementation from this draft yet: several measurable gates are not sufficiently operationalized, and one split-description ambiguity could allow final-opponent or seed leakage.

## Antithesis (steelman)
The strongest alternative is to defer both the 10k throughput gate and broad learning changes, first run a small, fixed-budget experiment against one non-open-space heuristic in the existing Python engine. That minimizes the chance of entangling simulator changes with reward/curriculum changes and makes attribution easier. The counterpoint is that G007 throughput is roughly 7.8x below the proposed gate and its rollout dominates optimization, so retaining profiling/optimization as an early independent lane is justified. Keep the lanes separately measured; do not require the throughput gate to be achieved before collecting useful strategy evidence if the approved plan explicitly permits bounded local learning experiments.

## Findings requiring revision

1. **Define disjointness at the right granularity (high).** The draft says final adversaries/seeds are unseen, but does not fully specify whether "unseen" means policy identity, implementation/configuration hash, seed, or all three; nor how validation opponents relate to training heuristics and their variants. Make a split manifest with immutable opponent IDs, code/config/model hashes, seed namespaces, and an explicit allowed-use matrix (`train`, `imitation`, `validation`, `final`). Specify that any exact final opponent policy/hash and final seed/game tuple is absent from train, demonstration generation, reward design, and validation. The exact open-space policy is correctly required final-only by the interview; ensure the final suite explicitly includes it and the >=60% gate is evaluated against it, rather than leaving “required final adversaries” undefined. Tests should reject forbidden hash/ID/seed overlap and fail closed when provenance is missing.

2. **Make the statistical promotion rule executable (high).** “Paired bootstrap 95% with multiple-comparison correction” and “adjusted confidence interval supports a significant decline” are not yet one reproducible test. State the paired unit (same seed × seat × opponent, with candidate and incumbent each evaluated on that exact game condition), score mapping, bootstrap resampling unit/strata, replicate count and RNG seed, one-sided decline hypothesis, family of primary opponents, and a specific correction procedure. Holm is naturally defined over p-values; if the implementation instead corrects intervals, name and test a valid adjusted-interval method. Define the promotion decision for insufficient/degenerate samples and missing opponent coverage as “do not promote.” Test synthetic no-regression, clear-regression, ties, and multiplicity examples. The final observed-win gate should state explicitly that draws are reported but do not count as wins, consistent with the user’s decision and draft acceptance section.

3. **Lock throughput denominator and timing protocol (high).** The draft usefully distinguishes arena transitions from agent observations, but “environment steps/s” remains overloaded across requirements, reports, benchmark CLI and stage timing. Define the principal numerator as completed two-agent arena transitions (one joint `step` = one environment step), separately report agent decisions/observations per second, and do not compare either to G007 unless the G007 raw report confirms the same numerator. Specify whether initialization/reset and Python observation construction are inside the end-to-end wall interval (they should be for useful rollout throughput), whether optimizer and checkpoint/export are included in wall-inclusive throughput, warmup policy, fixed game/config/random seed/action stream, number of repeats and summary statistic/spread. Use the G007 comparable profile as a clearly labeled reference if its measurement boundary cannot be reconstructed. The `torch.profiler` trace is diagnostic, not the acceptance timer; profiling overhead must not contaminate the >=10k result.

4. **Reconcile the 10% candidate gate with the 10k terminal gate (medium).** “>=10% over prior candidate (or required to attain 10k)” can induce repeated low-value experiments and does not bound how many ports are attempted. Define a small maximum experiment ladder: baseline, one low-risk transfer/loop intervention, NumPy control, then at most one compiled first candidate (Numba if compatible); stop exploring a branch after parity failure or no repeatable gain. Treat 10k as a hard G008 approval gate, not as evidence that an isolated kernel speedup suffices. Report cold JIT/import and steady-state rates separately; accept backend only on repeated representative end-to-end improvement and parity. Rust/PyO3 should remain out of this G008 implementation unless a measured profile and a bounded build/toolchain trial justify it.

5. **Bound Kaggle spend and preserve a recovery path (medium).** “Small bounded fraction,” “quota floor chosen by orchestrator,” “bounded experiments,” and “time/output limits” do not supply an enforceable budget. Before each remote batch, record current quota and define a numeric stop threshold/reserve in GPU-hours plus maximum kernel wall time, output size, and submission count; do not presume the previous G007 quota remains current. Reserve evaluation/ONNX validation budget before training. Persist resumable checkpoints and run IDs before expensive jobs; stop safely at the budget floor without billing changes. If no quota is available, finish local design/CPU parity work but do not report CUDA throughput or learning gates as passed.

6. **Scope schema and browser changes narrowly (medium).** Historical `lc-run/1`/`lc-eval/1` compatibility is appropriately called out. Before a schema bump, identify exactly which G008 evidence cannot be represented in current schemas; add a versioned schema rather than changing `lc-eval/1` semantics, and prove old G007 bundles remain viewable/valid. Avoid modifying viewer display/schema solely to host the internal league; tournament UI remains out of scope. Single-file ONNX and real local browser acceptance remain a sound release gate.

## Trade-off tension
A strict untouched final suite gives credible generalization evidence but makes iteration intentionally slow and one-shot; using it to tune opponents, rewards, or checkpoints would make the 60% result selection-biased. Conversely, a validation suite large/diverse enough to support repeated promotion can itself be overfit. The sound balance is a hashed, immutable final suite used only after candidate freeze, plus a sufficiently broad but separate validation matrix for all promotion decisions; if final evaluation fails, do not retune on that suite—collect a new future holdout cycle.

A second tension is end-to-end speed versus implementation risk: an optimized simulator can make more rollouts possible but semantic drift corrupts both training and evaluation. Keeping the scalar engine as oracle and requiring state/observation/reward/result differential parity is the right boundary; avoid promoting a backend based on microbenchmark throughput alone.

## Synthesis / requested draft edits
Keep Option A and its staged order. Before Critic review, revise the plan to:
- define the final set (including exact open-space) and machine-checkable train/validation/final opponent and seed/hash matrix;
- specify a single paired regression statistic and multiplicity decision procedure, with deterministic synthetic tests;
- define `env_step` and all acceptance timing boundaries in the benchmark schema, including G007 comparability limitations;
- set a finite candidate ladder and explicit parity/no-gain stop rules;
- state per-batch numeric Kaggle quota/runtime/storage/submission budgets and a checkpoint/recovery rule;
- retain the explicit “all gates or G008 not approved” outcome and prevent any final-suite access by promotion code.

## Evidence / source alignment
- The G008 context reports G007 at about 1,275 env steps/s, 3.195 s rollout vs 0.018 s optimizer; this supports profiling simulation/action/data transfer before any second-GPU proposal.
- The reviewed `training/ppo/train.py` collects observations and actions in a Python loop; lines 210–218 show per-tick observation construction and `sampled_actions.cpu().tolist()` synchronization, and lines 239–245 loop scalar engine steps. This supports targeted profiling and batched transfer work, not a presumption that Numba or Rust will win.
- The draft’s exact-open-space-final-only constraint, hard gates, historical schema compatibility and ONNX browser gate are sound and should be preserved.
- Official PyTorch profiler/CUDA/benchmark APIs are useful diagnostics, but the prior Kaggle image used PyTorch 2.11 while the cited docs are 2.14. The implementation plan must feature-detect/use the installed runtime and record versions; do not assume identical API behavior or profiler availability. Pin-memory/non-blocking changes are workload-dependent, so retain only if the end-to-end benchmark demonstrates gain.

No implementation performed. Sequential Architect review is not approval to begin G008 execution; after these edits, proceed to the planned Critic review. If the draft is revised as requested, the architecture is likely approvable without adding DDP, full Rust port, or a league UI.
